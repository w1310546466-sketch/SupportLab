# 这一步学什么：把事实、结论和待核实事项分开

2026-10-06。核心目标：模型说出的诊断需要能对上实际查到的证据，不能因为查过资料，就允许它随意补充建议。

## 从 018 看变化

上次模型正确判断“月度配额耗尽”，却又建议申请额外配额。我们的资料没有说明是否支持申请，不能把它当作确定的解决办法。
现在将答案分成三部分：

| 部分 | 本次实际内容 | 谁负责 |
| --- | --- | --- |
| 已查证事实 | 当时频率 2/60，月度用量 1000/1000 | 程序从实际工具反馈填写，不让模型重新编写数字 |
| 诊断结论 | 该次历史请求的证据支持月度配额耗尽 | 模型选择原因和证据；程序核对错误码、数字、请求时间和规则 |
| 待核实事项 | 今天是否恢复需要当前状态；能否增加额度需要服务规则 | 模型选择有限的待核实项目；程序使用明确表达不确定性的文字 |

最终中文答复由程序组织。模型仍决定查哪些工具、使用什么参数、选择哪个原因和哪些证据；显示文字受到约束。
这不是模型自由生成文字后，另一个模型给它打分，也不是能理解任意句子的通用裁判。

## 一份资料有一个短编号

工具返回结果时，程序现在给它附上 E1、E2、E3 这样的编号，就像给资料贴上书签。
模型在答案里注明“依据 E1 和 E2”，程序就能找到它实际读过的材料。
这些短编号由程序生成并放进模型能读到的结果正文，不由模型自己编造。
`req_demo_018` 仍是用来查业务的请求编号；E1 是本次查询返回的证据编号。

修订后这次真实轨迹：

1. 模型先提出查请求，程序返回 E1：配额错误码和发生时间。
2. 模型在下一条回复里同时提出查账号、查文档。程序依次执行，返回 E2 和 E3。
3. 模型选择配额原因、E1、E2 和配额规则引用，程序检查通过后组织答案。

共有 3 次模型请求、3 次工具调用、4 轮本地动作。本次组合顺序和上次不同，检查器不要求固定顺序。

## 检查能挡住什么

已实际运行四个离线例子：

| 例子 | 实际结果 | 理由 |
| --- | --- | --- |
| 配额诊断有证据，建议标为待核实 | 接受 | 请求、数字、规则一致 |
| 引用真实配额规则，却选择频率超限 | 拦下 | 原因与错误码、数字不符 |
| 诊断正确，但提出立即增加配额 | 拦下 | 不在允许的待核实事项中，没有已验证操作机制 |
| 未查询账号，就给确定诊断 | 拦下 | 没有对应的账号证据 |

后三条是故意构造的程序测试，不是声称真实模型恰好犯了这三种错误。四项都符合预期，不能称为模型准确率 100%。

在项目目录运行下面这条即可看全部结果，**不调用 DeepSeek、不消耗 API 额度**：

```powershell
.\.venv\Scripts\python.exe -m supportlab answer-demo
```

## 本次真实运行也经历了一次失败

第一次真实复验，三个工具均返回成功，但最终提交的证据引用没通过检查，程序停止并转人工。
当时仅保留了 `missing_evidence`，没有保存模型具体提交的引用编号，因此不能追溯它究竟写错了什么。
这个失败暴露了可观察性不足，也提示我们应减少复杂编号的复制要求。

修订后，把短证据编号写进工具反馈正文，并记录模型选择的短编号与可用证据列表。第二次复验通过。
这是一次根据失败进行的设计修订，不是对同一版本反复调用得到的稳定性结论。

## 学习与工程边界

当前检查只适用于现有固定版本两种 429，使用明确的原因标识和两个待核实选项。文档指纹、原文规则行也会核对，文档修订后需要重新审查相应规则。
这是减少无依据诊断的取舍：牺牲部分自由表达，换来更明确的程序检查。它不能代替通用语义理解、未知故障排查或人工抽查。
该阶段的追问和转人工仍允许简短文字，未做同样的逐项证据核验。后续已改为有限停止理由检查与程序生成摘要，见 [下一阶段记录](clarify-and-handoff.md)。
程序没有自动重试或联系真人；本轮没有实现任务恢复、工单写入或新业务工具。
旧 `agent-mock` 继续使用旧的手写输出，方便回归。不能把它与新增检查后的真实版直接当作公平架构对照。

最新完整测试为 122/122，通过时间 8.819 秒；旧 mock 开发场景 20/20，新的离线演示 4/4。
初版 121 项通过后，因真实引用失败修订并增加日志测试，才形成当前 122 项。旧的中间报告也保留。
018 已用于开发与修订，真实验证仍只有这一个业务案例，人工复核状态仍为待完成。

## 可选练习与参考答案（15–20 分钟）

先读正确例子的三部分答案，再运行：

```powershell
.\.venv\Scripts\python.exe -m supportlab answer-demo --case unsupported-advice
```

预期：程序显示拦下无依据建议；命令本身正常退出，因为“拦下”正是测试要看到的行为。
用自己的话解释：为什么“核实能否申请额外配额”可以保留，而“立即申请即可恢复”不能直接发布？
参考答案：前者明确承认缺少规则，需要补证据；后者承诺了资料没有证明的能力和效果。
练习不阻塞下一步；这次实现和答案演示仍由 AI 完成，不能算作用户已独立掌握。

运用 AI 的方法：让 AI 把查到的事实、根据事实作出的判断、尚待核实的建议分开，并分别指出依据。
如果要写程序落实要求，还应把能确定的部分写成检查规则；一句“不要编造”无法证明要求已经执行。

本阶段之后已实现追问与转人工摘要；实际验证及仍存在的模型格式失败见 [后续记录](clarify-and-handoff.md)。
