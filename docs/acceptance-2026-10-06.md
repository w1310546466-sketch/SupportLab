## 本轮发现及修复

首次运行的 15 个失败案例共有 25 个失败步骤；报告列出的失败均是文档问答结果缺少 `result.usage.tool_calls`，预期该字段为整数 `0`。其余已定义的结果、诊断、状态和引用检查通过。因此问题属于返回结构和用量可观测性不一致，不是 15 次错误诊断。

应用修复只涉及 `supportlab/rag.py`：统一所有 RAG 返回的 `tool_calls: 0`，保留已有模型调用、token 和耗时信息；版本从 `extractive-rag-v2` 更新为 `extractive-rag-v2.1`。没有修改诊断规则、放松评分或更改原测试预期。

由于首次结果参与了修复，相关的五个场景家族、共 25 题已登记为开发材料：

- `compound_failure_precedence`
- `context_preference_lifecycle`
- `interleaved_pending_sessions`
- `revision_across_pending_task`
- `same_target_reclassification`

处理记录见 [暴露情况登记](../evals/holdout_v1.disposition.json)。整个原 40 题后续重跑都标为回归；**40/40 不能替换首次 25/40，也不能与新 12/12 相加宣称 52/52 保留测试通过。**

## 场景范围

原集 `composition-holdout-v1` 含八个家族，每家族五题：

| 家族 | 检查的组合行为 |
| --- | --- |
| 相同编号重新分类 | 插入文档问答后，复查编号应重新取证并反映已变化的故障 |
| 分阶段修复资料 | 两处问题先修一处仍停止，两处均修复后恢复诊断 |
| 多会话交错 | 一个会话等编号时，另一个会话设置偏好或排查；各自状态保持正确 |
| 等待期间文档变化 | 文档变化、索引失效、重建与还原，不绕过固定规则的版本检查 |
| 不同账号的同名编号 | 查询和修改只作用于可信账号范围，不能混用其他账号记录 |
| 多种失败同时出现 | 资料缺失、证据冲突、版本异常等同时存在时，停止理由和查询范围正确 |
| 用户主张与保存证据冲突 | 用户自述、伪造证据编号或要求重试不能替代应用实际取得的证据 |
| 上下文与偏好的生命周期 | 长历史、取消、遗忘、跨用户偏好及用量统计的相互作用 |

新集 `composition-holdout-v2-supplement` 含三个新组合家族，每家族四题：

| 家族 | 检查的组合行为 |
| --- | --- |
| 检索入口的可用性隔离 | 只供 RAG 使用的指南缺失时，诊断检索仍可用；还原相同资料后 RAG 恢复 |
| 文档指令包含请求编号 | `/docs` 带编号仍进入文档问答，普通编号消息才排查；已有任务不会被文档问题覆盖 |
| 请求编号边界与续接 | 拼接、前缀、大小写或超长编号不能被截断成旧编号；等待时插入文档问题，再补合法编号恢复 |

这些是 AI 构造的模拟场景；作者见过实现。家族按完整交互组合区分，基础故障、业务规则和部分机制与开发测试共用。家族名不重复的自动检查不证明语义独立，不代表增加了新的故障根因，也不是第三方盲测。所有报告的人工复核状态仍为 `pending`。

每个案例使用临时业务数据库、文档副本、知识索引和会话存储；工具期间核对业务资料没有被修改。每步重新创建会话服务，检验保存状态后的接续；这不等于每步都跨进程，更不等于模型调用中途崩溃可以恢复。默认演示数据库和用户历史未被这些场景修改。
