# 对话与检索优化，以及固定流程对照

用户希望先完成工程优化，再统一了解实现；此处保存证据和取舍，供之后回顾。

## 发现了哪些问题

先构造 `conversation-dev-v1` 的 20 个开发案例并运行旧代码，得到 12/20。保留 [优化前报告](../reports/quality-before-2026-10-06.json)。失败包括：

- “API 支持退款吗”“如何申请发票”“训练参数”会因泛词返回无关资料。
- 英文认证、配额表述无法召回已有规则。
- 诊断之后问“为什么会出现 401 错误”，会重新诊断旧请求。
- “认证失败是什么意思”会误进等待请求编号。
- 等编号期间插入文档问题，被等待状态拦住。

## 实际修改

路由现在先处理明确的 `/docs` 与完整请求编号，再区分知识问题、文档主题追问、排查请求和请求指代。保存路由版本和原因，便于定位走错分支。它仍是显式规则路由，不是通用意图理解模型。

文档检索过滤泛化提问词，补充少量中英文别名；候选先按 FTS5 的 BM25 排序后截取，再按业务词权重排序。没有充分词面命中就不调用模型。这个改动依据实际开发失败，不代表向量或语义检索已实现。FTS5 的排名及排序方式依据 [SQLite 官方说明](https://sqlite.org/fts5.html#sorting_by_auxiliary_function_results)。

等待编号期间的知识问答使用独立路径，不覆盖待恢复的检查点；会话仍标记为等待状态，历史摘要保存最近文档主题。泛指追问使用原主题，新的错误码优先，避免不断把旧问题拼接长。文档问题超过上限时明确要求缩短，取消原有静默截断。

表格证据仍保存原始行与引用；展示时使用原表头把单元格写成“字段：值”。零命中、旧索引或缺资料时不创建模型对象；来源不可用会正常返回原因，不使整个会话停留在程序崩溃状态。`/usage` 只汇总已经持久化的记录，明确说明未知和遗漏范围。

## 同一个模型的两种控制方式

`workflow`：程序按固定流程调用工具，遇到资料缺失、冲突或失败停止继续取证；已有反馈交给 DeepSeek 形成最终结构化结论，仍通过原有证据检查。固定流程在工具收集阶段不让模型决定下一步。

`agent`：同一个 DeepSeek 模型自行选择工具并决定何时结束，使用同一执行器和最终检查。两组均最多 4 次模型请求、4 次工具尝试、8 轮决策，单次输出上限 768 tokens，网络自动重试为零。

两组读取同一个临时业务数据库与同版本文档，工具白名单、账号范围和上限一致；取证实际消耗分别记录，不强制获得相同数量的资料。评分不要求逐字答案或完全相同的调用顺序，检查结果动作、原因、证据契约及预算。

有一处必要差异：DeepSeek Chat Completions 不支持插入并非模型生成的原生工具调用。因此固定流程把实际工具结果放入应用证据包，动态 Agent 则沿用原生工具调用/反馈消息；两种控制提示也不同。这些差异在报告披露，不能把试验当作仅改变一个变量的严格架构因果实验。[DeepSeek 官方工具说明](https://api-docs.deepseek.com/guides/tool_calls/)

默认 `compare` 完全离线，回复由规则构造，只验证对照程序。只有显式 `--live --case ...` 才使用真实模型；一次只运行一个受支持案例，两组总上限 8 次模型请求。固定流程中模型若试图追加工具调用，会被拦下。

## 复现

实际验收（2026-10-06）：**204/204 程序测试通过**，最终运行 31.538 秒；新增 17 项针对路由、缺资料、续接、用量统计、固定流程边界和对照评分的测试。离线对照两组各 6/6，通过的是程序验证，API 为零。

同一 `req_demo_017` 的一次真实运行如下：[完整报告](../reports/comparison-live-rate-2026-10-06.json)。

| 配置 | 证据检查 | 模型请求 | 工具调用 | 输入 / 输出 tokens | 本次耗时 |
| --- | --- | --- | --- | --- | --- |
| 固定流程 + DeepSeek | 1/1 通过 | 1 | 3 | 2196 / 69 | 3063.058 ms |
| 动态 Agent + DeepSeek | 1/1 通过 | 4 | 4 | 10488 / 548 | 10968.979 ms |

两组都诊断为频率限制，引用相同的规则行，数字来自同一时刻的 61/60 与 999/1000。总计 5 次 API、13301 tokens，未计算金额。

动态 Agent 查了请求与账号，又进行了两次文档检索；第三次模型回复发生 JSON 语法错误，第四次在原预算内纠正，之后证据检查通过。`format_recovery.status=parsed`、`correction_requests=1`，这是本项目首次实际观察到真实格式纠正分支成功；仍只是一次观察，不能证明稳定恢复率。非法原文未保存，只有安全诊断信息，不能猜测具体错写了什么。

这个案例中固定流程消耗较少，保留这一结果。对照没有随机交换顺序、重复运行或覆盖广泛业务，且提示与证据载体有差异，因此不据此判定架构普遍优劣。下一步应扩充故障证据与保留测试，基于有额度的重复运行再评估稳定性。

```powershell

.\.venv\Scripts\python.exe -m supportlab kb-build

# 需要真实复现时才运行；会产生 API 调用
.\.venv\Scripts\python.exe -m supportlab compare --case rate-ok --live --output reports/my-comparison-live.json
```

优化后 20/20 是同一批开发题的复验，所有题目都参与了优化，真值由 AI 构造且仍待用户抽查。报告分别统计必要证据命中和无资料时正确停止；这些规则不证明任意引用都相关或答案完全正确。锁定测试、重复稳定性、更多业务故障和通用提示注入评估仍未完成。
