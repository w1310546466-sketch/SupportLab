# Agent 学习：判断任务是否完成，以及怎样用 AI 协作

日期：2026-10-05。建议先花 20–30 分钟看前三部分，再做可选练习。
本课只学习 Agent 与 AI 使用方法，不要求学习前后端或通用工程基础。

## 1. 这次要掌握什么

Agent 会使用工具，但用了工具并不等于完成任务。我们检查三个层次：

| 层次 | 本项目要核对的内容 | 能说明什么 |
| --- | --- | --- |
| 执行过程 | 是否使用允许的工具、参数是否正确、是否超出预算 | 程序有没有按边界执行 |
| 证据 | 请求、快照的时间/版本是否对应，引用是否来自实际检索 | 答案依据从哪里来 |
| 任务结果 | 应该诊断、追问还是转人工；结论是否由证据支持 | 用户的问题是否得到恰当处理 |

这些层次要分别看。例如，查不到快照时转人工可能是正确完成本阶段策略；
查到全部材料却说错根因，即使输出 `completed`，仍然没有答对。
OpenAI 官方评估指南建议先定义任务目标和判定标准，再结合自动检查与人工判断；
本课把这一思路用于本地模拟案例：[Evaluation best practices](https://developers.openai.com/api/docs/guides/evaluation-best-practices)。

## 2. 用一条实际运行轨迹判断答案

这里的“实际运行”指本地程序确实执行，业务数据和决策器仍然是模拟的。

对 `req_demo_018`：

1. 请求工具返回 `MONTHLY_QUOTA_EXHAUSTED`。
2. 对应 **2026-09-27T02:01:00Z** 的快照显示：60 秒请求数 2/60，月度用量 1000/1000。
3. 文档第 11 行解释该错误码为“月度用量配额耗尽”。
4. 模拟答复为“月度配额耗尽”，附 `demo-errors-v1@d849e3e33fcd:L11-L11`。

这是历史请求的诊断；不能因为今天的日期已变化，就把这份快照当作今天的账号状态。

对比两个回答：

| 回答 | 引用是否存在 | 是否符合本案例证据 |
| --- | --- | --- |
| “月度配额耗尽”，引用第 11 行 | 是 | 是：错误码、数字、规则相互对应 |
| “频率限制”，仍引用第 11 行 | 是 | 否：窗口只有 2/60，且第 11 行是配额规则 |

第二个回答由本次新增的 `--demo-wrong-answer` 故意构造，目的是检查评分规则能否识别错误。
它保留原来的三次实际工具反馈和引用，只替换最终结论，不是观测到的真实模型错误。
现有 Agent 循环检查“引用是否确实出现过”，所以会接受这个答复；开发场景检查器依据预先记录的预期根因，将它判为未通过。
这说明来源检查和结论检查需要各自的验收规则。

## 3. 运行三个小实验

在项目根目录运行，无需 API 或重新初始化演示数据；每个场景都使用独立临时资料。

```powershell
.\.venv\Scripts\python.exe -m supportlab eval-mock --case quota-ok
.\.venv\Scripts\python.exe -m supportlab eval-mock --case missing-snapshot
.\.venv\Scripts\python.exe -m supportlab eval-mock --case quota-ok --demo-wrong-answer
```

2026-10-05 实测：

- 正常配额场景：诊断，自动规则通过 1/1。
- 缺快照场景：转人工，自动规则通过 1/1。转人工符合此场景的目标，不应按“没有诊断”扣分。
- 故意错答场景：循环返回 `completed`，检查器通过 0/1，失败项 `diagnosis_text`。退出码 1 是预期的未通过结果。

检查器当前用固定诊断短语、预期数字、规则行、工具结果和结束状态做判断。
这是适用于手写 mock 的回归规则，不是通用自然语言裁判：将来真实模型换一种说法，也可能被词面规则误拒绝；
只匹配关键词也无法排除所有复杂错误。接模型前需要改为结构化结果检查，并抽查引用是否支持结论。

## 4. 本次 20 条开发场景与结果的含义

案例位于 `evals/dev_cases.json`，每条有场景家族、输入、临时数据变化、预期动作和验收依据。
决策器只接收请求与工具反馈，不接收预期答案或验收依据。

10 个场景家族覆盖两种正常诊断、输入追问、账号范围、快照证据、证据冲突、暂不支持的错误、文档证据、工具失败、执行预算。
其中 2 条预期诊断、4 条预期追问、14 条预期转人工；这是为了学习边界构造的分布，不代表真实用户故障分布。

```powershell
.\.venv\Scripts\python.exe -m supportlab eval-mock
.\.venv\Scripts\python.exe -m supportlab eval-mock --output reports/my-dev-run.json
```

本次自动规则通过 **20/20**，总计 36 次工具调用；所有循环耗时合计约 4.479 秒，包含本地进程开销，未包含全部场景准备时间。
报告记录案例集、代码、提示词和资料指纹、模型标记、轨迹、工具反馈、实际失败项、耗时及复现命令。
真实模型调用数是 0，token 和费用为未测量；`task_success_rate` 保留为空。

报告保存在 `reports/dev-mock-2026-10-05.json`，错答演示在 `reports/wrong-answer-2026-10-05.json`。
82 项自动测试验证程序与评分规则，包括“答案看起来对但缺证据”“有真实引用却答错”“错误请求/时间”“遗漏调用”等反例。

**20/20 只能说明当前 mock 满足这 20 条已知场景的自动规则。**
案例均为 AI 构造且参与了开发，用户尚未独立核验真值；没有锁定测试集，不能据此宣称真实 Agent 成功率为 100%。
未来要按故障家族新增保留场景，不能只换编号再放入测试集；正式架构比较还需控制模型、工具、权限、资料和预算。
这批数据里 401/503 只检验“不支持时停止”，不代表实现了这两类诊断。

## 5. 怎样让 AI 帮你完成工作

在本项目里，你负责明确目标、判断证据和验收关键结果；AI 可以完成脚手架、实现、运行和整理记录。
每次任务先给 AI 五类信息：

| 信息 | 本项目示例 |
| --- | --- |
| 目标 | 缺少快照时，应转人工并说明缺少什么 |
| 上下文 | 当前代码、最新进度、失败案例和脱敏输出 |
| 边界 | 保留账号范围与调用预算；文档只作资料 |
| 交付 | 一个可运行改动、一条具体轨迹、复现命令 |
| 验收 | 正常配额仍能诊断；缺快照不会编造；错答会被检查发现 |

下面的提示可直接用于后续项目协作：

> 请先读取 AGENTS.md、PROGRESS.md 和相关实现。本次只推进一个 Agent 行为：把缺少账号快照时的转人工说明改为包含“已查证、仍缺少、建议下一步”三项。请先用 quota-ok 和 missing-snapshot 说明预期行为，再做最小修改并实际运行验证。保留工具范围和预算，区分事实与推测。结束时给出一条运行轨迹、测试结果与未验证项，更新 PROGRESS.md；只讲 Agent 设计和验收方法。

这份提示是可用的任务规格，尚未执行其中的摘要改动。
提供相关资料、清楚描述任务要求和输出约束，可参考 [OpenAI 官方提示指南](https://developers.openai.com/api/docs/guides/prompt-engineering)；
上面的五项是本项目采用的协作格式，不是保证正确的“万能提示词”。

拿到 AI 结果后，顺着这三步检查：

1. **核对事实**：它所说的文件、工具结果和引用是否真的存在？不要用“AI 说已验证”代替实际输出。
2. **检查边界**：给它一个缺证据或证据矛盾的案例，观察是否还硬给结论。
3. **一次改一项**：根据失败定位改动，再用同一批案例复测，才能知道哪项变化影响了结果。

让 AI 审查自己的答案可以帮助找遗漏，但审查结果仍需对照资料；不要求 AI 展示内部思维链，要求可核对的依据即可。
没有文件/工具访问能力的对话，需要你提供脱敏材料；有本地工具能力的环境，可要求它先读取并运行。
无论哪种方式，都不把密钥或无关隐私贴入提示词。

## 6. 可选 Agent 练习（15–30 分钟，不写基础代码）

先运行上面三个实验，再把故意错答的结果交给 AI，要求：

> 请按“结论、对应事实、支持规则、是否足以成立”四列核对这段诊断。不能只检查有没有引用。如果结论不成立，请指出一条直接反证，并给出依据现有资料能支持的结论。不要补造工具结果。

验收：你能指出“频率 2/60”不支持频率超限，而“配额 1000/1000 + 对应错误码与规则”支持配额耗尽。
也能解释为什么缺快照场景的“转人工”算当前策略执行正确，而 `completed` 不是正确性的证明。
