# SupportLab：现在怎样连续使用

已支持等待编号期间插入文档问题、沿用文档主题追问、零命中时跳过模型加载，以及 `/usage` 用量查看。另有认证、权限、上游事件与超时执行未知路径，新环境使用前运行 `init-demo --extended` 和 `kb-build`。下方实验数字保留各阶段记录，最新概况与运行入口见 [README](../README.md)。

你可以把当前项目理解成一个有资料库、有查询工具、能记住当前排查任务的故障助手。它诊断的是虚构服务，DeepSeek 提供真实模型能力。

先看一条完整例子：你说“帮我排查”，程序发现没有请求编号，保存“正在等编号”的状态。即使退出后重新打开，你补上 `req_demo_018`，它仍能继续。模型查询请求、账号快照和规则，程序核对证据，最后回答“那次历史请求因月度配额耗尽而失败”。你再问“再查一下刚才那个请求”，它沿用编号，但重新查询工具。

## 五块功能分别做什么

| 功能 | 在这个例子中负责什么 | 目前做到的范围 |
| --- | --- | --- |
| 工具 | 查失败请求、当时账号数字和规则 | 三个只读工具；白名单、参数、账号范围、时限与次数由程序执行 |
| RAG：先检索再回答 | 问“429 是什么”时，从资料中找规则再回答 | 四篇模拟文档、32 个片段；关键词与有限别名检索；模型选择实际引用，程序输出原文 |
| 历史 | 记住这个会话之前问过和回答过什么 | 本地保存，退出再打开仍在；新会话历史独立 |
| 偏好 | 明确要求简洁回答后，影响后续诊断展示 | 支持详略、段落/列表；同一模拟用户跨会话保存，可查看和删除 |
| 上下文 | 这一次究竟给模型看哪些相关信息 | 偏好、程序维护的任务摘要、最近最多四轮片段，总预算 3600 UTF-8 字节；当前消息与本轮工具反馈另算 |

“历史”是保存下来的记录，“上下文”是这次选择给模型看的内容，“偏好”是你明确设置的表达方式。它们职责不同。模型不会自动看到整个磁盘；也不会因历史里有人写“换成另一个账号”而取得权限。

任务摘要保存最近编号、结果类型和已核验原因，明确标记为历史参考。它是程序从结构化结果提取的少量字段，不是模型自由总结，也不是完整长期知识记忆。历史里的普通文字不会被提升为系统规则。

## 启动与继续

在项目目录运行：

```powershell
# 零 API 模式，适合先体验
.\.venv\Scripts\python.exe -m supportlab chat --session learn1
# 真实 DeepSeek 模式，使用现有本地配置
.\.venv\Scripts\python.exe -m supportlab chat --session ds-learn1 --live
```

输入以下对话：

```text
以后回答简洁一些
帮我排查
req_demo_018
/docs 429 是什么意思
再查一下刚才那个请求
/history
/context
/exit
```

018 的预期诊断：当时频率为 2/60，月度用量为 1000/1000，证据支持“月度配额耗尽”。这是 2026-09-27 的模拟历史记录，不能证明今天的用量或恢复情况。

新增编号：`req_auth_revoked`（撤销）、`req_auth_expired`（过期）、`req_permission_missing`（缺少权限）、`req_upstream_incident`（关联上游事件）、`req_timeout_unknown`（执行结果未知，转人工核实）。均使用原来的三个只读工具，证据不足时停止；不修改密钥、权限，也不自动重试。详见 [场景与验证记录](diagnostics-2026-10-06.md)。

用同一个会话编号重新启动会保留历史、任务和运行模式；即使省略 `--live`，既有真实会话仍然调用模型。每条诊断最多四次模型请求，文档问答最多两次；一段不限轮数的聊天没有整体费用上限，`/exit` 结束。`/prefs` 等管理命令、等待编号均为零 API。

也可以逐条发送并保存结果：

```powershell
.\.venv\Scripts\python.exe -m supportlab chat --session learn2 --message "帮我排查"
.\.venv\Scripts\python.exe -m supportlab chat --session learn2 --message "req_demo_018" --output reports/my-chat.json
.\.venv\Scripts\python.exe -m supportlab sessions
```

## 常用输入

| 输入 | 作用 |
| --- | --- |
| `req_demo_017` / `req_demo_018` | 排查指定请求；前者频率限制，后者月度配额耗尽 |
| `帮我排查` | 缺编号时暂停并追问 |
| `再查一下刚才那个请求` | 沿用当前编号，重新取证 |
| `/docs 401 是什么` | 明确走文档问答；当前 401/403/5xx 仅有知识说明，不能据此断定具体根因 |
| `以后回答简洁一些` / `以后回答详细一些` | 两种已支持的明确偏好表达 |
| `/prefer detail brief` / `/prefer detail detailed` | 调整诊断详略 |
| `/prefer layout bullets` / `/prefer layout paragraphs` | 调整诊断为列表/段落 |
| `/prefs` / `/forget-preferences` | 查看/删除偏好 |
| `/history` | 查看此会话最近 20 轮问答；管理命令不计入问答历史 |
| `/context` | 查看下一轮将使用的历史参考包及大小 |
| `/usage` | 查看本会话已保存轮次的 API/工具次数与已知 token；不含未保存中断调用，不是账单 |
| `/cancel` | 清除当前任务与检查点；保留历史、偏好 |
| `/new` | 交互模式新建同运行方式会话，偏好保留 |
| `/exit` | 退出；下次可继续 |

路由目前由程序的关键词规则决定；不理解任意含糊表达。有歧义时用 `/docs` 指定知识问答，或明确给请求编号。等待补编号时可先问知识问题，程序保留等待位置，之后继续补编号或 `/cancel`；“详细解释一下”沿用文档主题，明确的新错误码优先。偏好仍只支持上述枚举，不从自由聊天中归纳个人信息。

## 资料如何流动

诊断路径：**当前消息 → 找到请求编号 → 整理历史参考 → 模型选工具 → 程序查模拟数据 → 结果回给模型 → 程序核对证据 → 按偏好展示 → 保存问答与任务摘要**。

文档路径：**问题 → 检索固定版本的资料片段 → 模型选择相关引用 → 程序确认引用来自本轮检索 → 输出原文与来源**。离线文档模式按检索排序选择前两条，不调用模型。模型选择了存在的引用，也不保证选择完整或最相关，因此仍需人工抽查。

资料索引存于 `data/knowledge.sqlite3`，会话与偏好存于 `data/memory.sqlite3`，暂停位置存于 `data/memory.checkpoints.sqlite3`。三者与模拟业务数据库独立。文档改变后旧索引拒绝使用，运行 `python -m supportlab kb-build` 重建；只能索引应用登记的四篇文件，不会遍历你的其他资料。诊断工具 `search_docs` 使用单独的三篇规则文档检索路径，两者不应混称。

本地检查点使用 LangGraph：缺编号时暂停，收到编号后恢复；已实际验证另一个 Python 进程恢复同一任务。[官方持久化说明](https://docs.langchain.com/oss/python/langgraph/persistence)、[中断与恢复](https://docs.langchain.com/oss/python/langgraph/interrupts)。如果程序在模型处理中崩溃，目前不自动重复该调用，而是说明中断并要求 `/cancel` 后重新排查；这不等于任意位置的精确恢复。

业务账号与用户标识由应用提供，模型不能切换。CLI 固定演示用户，并非登录平台。输入进入历史和检查点前会过滤常见密钥形式，但这不是通用隐私识别；不要往业务聊天中粘贴真实密钥。当前未启用 LangSmith 云追踪。

## 这次实际跑出了什么

以下为首次功能版的历史验证；当前优化的验证与局限见 [优化记录](optimization-2026-10-06.md)。

- 程序检查：187/187，通过了跨进程续接、用户隔离、旧答案不能代替新证据、上下文预算、偏好校验、引用检查及原功能回归。
- [离线演示](../reports/app-offline-2026-10-06.json)：13/13 功能检查，零 API；使用临时数据库。
- [真实演示](../reports/app-deepseek-2026-10-06.json)：续接 018 诊断用了三次模型请求、三个工具；文档问答用了一次模型请求。合计输入 7427 / 输出 308 / 总计 7735 tokens，演示总耗时约 10.86 秒，未触发格式纠正。共 11 项检查通过，其中多项是本地历史/偏好行为，不是 11 个模型案例。
- 固定 `langgraph==1.2.13`、`langgraph-checkpoint-sqlite==3.1.1`、`openai==3.24.0`，完整依赖锁定 43 项；依赖一致性检查通过。接口依据 [DeepSeek 官方文档](https://api-docs.deepseek.com/api/create-chat-completion/)；无工具的文档问答省略工具选项。

仍未完成：向量检索、复杂长期记忆、完整 401/403/5xx 业务诊断、自动工单、网页产品、固定流程与 Agent 的公平对照、锁定测试集。离线固定流程不使用模型，不能拿它与真实 Agent 的差别直接证明架构优势。费用未根据价格计算，报告保留实际 token。

## 一个可选的 15 分钟练习

先启动离线会话并设置简洁回答，发“帮我排查”后退出；再次用同一个会话编号启动，补 `req_demo_018`。接着 `/new`，查看 `/prefs` 和 `/history`。

预期：旧任务能续接；新会话保留简洁偏好，但没有旧问答。再排查 017 时应该得到频率原因，不能套用 018 的配额结论。这说明“记住表达偏好”“保留某次任务”“重新查业务事实”是三件事。练习可跳过，不阻塞开发。

本次运用 AI 的方法：把“加记忆”改写成可验证行为。例如：“重启后能继续；新会话保留明确偏好；其他用户看不到；旧答案不能当本轮证据。请实现并给一条完整运行轨迹及失败边界。”这样的要求能让 AI 同时交付功能和可检查的证据。
